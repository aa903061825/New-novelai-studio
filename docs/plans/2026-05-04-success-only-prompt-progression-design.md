# 成功后才推进提示词设计

## 目标

把当前“失败最多重试 3 次后可能重新生成 payload”的行为，改成“无上限重试当前 payload，只有真正成功生成并保存图片后才推进到下一条 prompt / 下一行”。

对用户可见的结果是：

- 同一行无论失败多少次，都会停留在当前行
- 只有某次请求真正成功并完成保存后，下一次生成才会进入下一行
- 用户仍可手动停止批处理，避免永久卡在错误状态

## 当前行为

当前生成主流程位于 `lib/ui/generation_page/view_models/generation_page_viewmodel.dart`。

现状是：

- `_cachedPayloadResult` 用于缓存当前 payload
- `_cacheRetriesCount` 限制同一 payload 最多额外复用 3 次
- 当缓存次数用尽后，即使一直没有成功，也会重新调用 `GeneratePayloadUseCase` 生成新 payload
- 如果 prompt 使用 `single_sequential`，重新生成 payload 时就会推进到下一项

因此当前实现并不是“成功后才推进”，而是“失败若过多，也可能推进”。

## 需求边界

本次只调整“失败后是否继续使用当前 payload、何时推进到下一条”的策略。

本次不扩展的内容：

- 不新增 429 专项处理
- 不新增自动退避、指数重试或 `Retry-After` 支持
- 不新增运行中断后的断点恢复
- 不改变 `currentBatchCount` 和 cooldown 的现有统计口径，除非实现时发现必须修正的耦合问题

也就是说，本次目标是把“推进条件”从“成功或失败超限后重新生成”收紧为“只有成功后重新生成”。

## 备选方案

### 方案一：直接移除失败重试上限（选中）

保留现有 `_cachedPayloadResult` 驱动思路，但不再使用 `_cacheRetriesCount` 控制切换时机。

规则改为：

- 有缓存 payload 时，一直复用该 payload
- 成功后清空缓存
- 停止批处理或重新开始批处理时清空缓存
- 只有缓存为空时，才重新生成新的 payload

优点：

- 改动最小
- 与当前架构最一致
- 最容易验证“只有成功才推进”

缺点：

- 仍沿用 viewmodel 内部缓存状态，没有把“重试策略”抽成单独模块

### 方案二：新增显式“当前行锁定状态”

在 viewmodel 中新增独立字段，明确表达“当前 prompt 已锁定，直到成功前禁止推进”。

优点：

- 语义更直观

缺点：

- 额外状态较多
- 与现有 `_cachedPayloadResult` 有部分职责重叠

### 方案三：重构为独立的重试/推进策略对象

把 payload 缓存、失败复用、成功推进都收敛为一个小型状态对象，由 viewmodel 调用。

优点：

- 可测试性最好
- 后续若要加回退避、恢复、策略切换会更容易

缺点：

- 比当前需求略重

## 选中方案

采用方案一的行为语义，但实现时允许把缓存逻辑整理成一个很小的辅助对象，以便测试。

换句话说：

- 行为上保持“无限重试当前 payload，成功后才推进”
- 代码上允许做最小限度的结构整理，以避免把测试全部压在异步网络流程上

## 详细行为

### 成功时

当请求成功、图片处理成功、文件保存成功后：

- 当前命令返回成功卡片
- `currentTotalCount` 加 1
- 清空当前缓存 payload
- 下一次调用 `nextCommand()` 时重新生成新的 payload

如果 prompt 配置使用 `single_sequential`，那么“重新生成新的 payload”这一步会自然推进到下一条。

### 失败时

当请求、响应校验、图片处理或保存过程抛错时：

- 当前命令返回错误卡片
- 不增加 `currentTotalCount`
- 不清空缓存 payload
- 下一次请求继续使用同一份 payload

因此，不管失败 1 次还是 100 次，只要中间没有一次真正成功，当前 prompt 都不会推进。

### 停止与重新开始

当用户点击停止批处理，或重新开始新一轮批处理时：

- 清空当前缓存 payload
- 不保留上一次失败中的“锁定行”

这样可以避免用户停止后再次开始时，意外继续复用上一次失败任务。

### 程序重启

本次不做运行态持久化。

因此程序关闭或重启后：

- 不恢复到上一次失败中的当前行
- 会像全新一轮批处理那样重新从初始状态开始

## 数据流

核心数据流如下：

1. `nextCommand()` 检查批处理状态
2. 若当前存在缓存 payload，则直接复用
3. 若没有缓存 payload，则调用 `GeneratePayloadUseCase` 生成新的 payload
4. 执行 API 请求
5. 若成功：清缓存、记成功数、继续下一次生成
6. 若失败：保留缓存、展示错误、继续下一次重试

关键点是第 2、3、5、6 步：

- 缓存存在时不重新生成
- 只有成功才清缓存

## 测试策略

本次至少覆盖以下回归点：

1. 同一个缓存 payload 在连续失败时会被无限复用，不会因为次数达到上限而丢弃
2. 成功后会清空缓存，下一次才会重新生成 payload
3. 当 prompt 使用 `single_sequential` 时，失败后重试仍停留在当前项，成功后下一次才进入下一项
4. `startBatch()` 和 `stopBatch()` 仍会重置缓存，避免脏状态跨批次泄漏

## 风险与兼容性

本次变更会让“持续失败时也会自动切到后续 prompt”的旧行为消失。

这是有意的行为变更，符合当前需求，但需要注意：

- 如果某一行 prompt 永远无法成功，批处理会一直卡在该行，直到用户手动停止
- cooldown 和 batch 计数仍会继续工作，因为当前实现把“命令完成一次”与“是否成功”区分开了

这也是本次设计选择保留的现有行为。
